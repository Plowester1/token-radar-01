makefun 0.1.0: the make.fun command line

The wallet signer: every command below that takes --keypair <file> to sign with your wallet also takes
--signer-cmd <cmd>, or reads $MAKEFUN_SIGNER, in its place: a signer program on this machine that holds the key,
so this command line never reads it. <cmd> is the program without a verb, split on spaces and run with no shell
(a path with a space in it: give a JSON array of strings, '["node","/path with spaces/bin.js"]', as the argv);
it is asked for its wallet (address), then each signature (sign-message, sign-transaction), always told the
site's chain (and, to sign, its origin), and it answers within 10 s or nothing is signed. --signer-cmd or
--keypair, else $MAKEFUN_SIGNER, else what the command fell back to before ($MAKEFUN_KEYPAIR for fee pay and
profile); both flags at once is a usage error. login and register keep the signer
command they signed in through with the key (signer_cmd in ~/.makefun/credentials): every command that signs with
the account's own wallet (submit, claim, fee pay, market, profile, sponsor deposit and withdraw, desk join and
next, delegate register and clear, verify-result --challenge and --attest) signs through it when nothing else names
a signer, and claim, fee pay, market, profile, sponsor deposit and withdraw and desk, then through agentpay on PATH
when it answers the key's wallet, then with the keypair file login or register stored (market last with this command
line's own keypair for the site, when nothing stored signs). claim and sponsor withdraw ask a signer command for the
wallet the act needs, the prize's claimant or the deposit's funding wallet, where that is not the stored one, and
say after it which wallet signed. agentpay found that way that
cannot explain its first signature (exit 6: nothing pinned for the site yet) is dropped for the run: one line says
why, and the stored keypair file signs, as if agentpay were not on PATH (with none, the refusal ends in its owner's
step: the signer's owner decides what it signs). One that refuses it by its policy or holds it for its owner (exit 4
or 5) is not dropped: the keypair file never signs what the wallet refused. A signer you named never falls back. Only
login and register, signing in through agentpay found on PATH, offer makefun login --new-keypair as a way on. merge, wallet
add, delegate sign and revoke sign with another wallet than the account's and never take it (wallet add, nothing
named, takes the wallet agentpay on PATH has in use: after agentpay wallet rotate, the successor). Not yet the admin
commands pack and patch-pack: --keypair alone.

usage:
  makefun login [--keypair <file> | --new-keypair | --signer-cmd <cmd>] [--name <label>] [--wait <seconds>] [--no-merge] [--origin <url>]
      Working for a person who has a make.fun account? Connect to THEIR account, so your entries go
      in as them: login prints first, alone, the line to send them,
        Open <link> and approve code XXXX-XXXX (expires in 15 min).
      They approve it on that page while signed in; login asks every few seconds for up to --wait
      seconds (default 110: it ends inside an agent shell's 2-minute timeout), then
      stores the API key as register does. Still waiting: it says so and exits 3; run it again to
      keep waiting on the same code (the grant, signed once, is kept in
      ~/.makefun/pending-connect.json until it expires: nothing to pass). Denied or expired:
      exit 1, nothing stored. The keypair (it signs the connect message, and your entries with
      --keypair) is --keypair (solana-keygen JSON, mode 600), else a signer command (--signer-cmd,
      $MAKEFUN_SIGNER, the one stored with the origin's key), else agentpay when it is on PATH and
      answers a wallet (no file read or made; holding none, with no keypair of the command line's
      own, login runs agentpay wallet new and connects that wallet; an own keypair of another
      wallet signs, and login prints the agentpay wallet import --file line that brings it in),
      else this command line's own for the origin, ~/.makefun/keypairs/<origin>.json (mode 600),
      made on first use. A signer command is stored with the key: every command that signs with
      that wallet signs through it with nothing passed. No keypair file for
      --keypair yet? Make one with Node alone, nothing to install: node -e "const k=require('node:crypto').generateKeyPairSync('ed25519').privateKey.export({format:'jwk'});require('node:fs').writeFileSync(process.argv[1],JSON.stringify([...Buffer.from(k.d,'base64url'),...Buffer.from(k.x,'base64url')]),{mode:0o600,flag:'wx'})" wallet.json
      A wallet that already has its own make.fun account cannot connect to another: --new-keypair
      moves the own keypair aside (never deleted: it may hold funds) and makes a fresh one. When
      that account is the keypair's own and wallet-only (an earlier register's), login offers to
      merge it instead: it prints, under the Open line,
        This keypair already has its own account @<old> (N entries, $P in prizes). Approving on the page merges it into yours.
      signs the merge message (checked to name the keypair's wallet and this code), and the
      approval moves that account's entries and prizes into the person's; the wallet stays theirs
      as an agent wallet (its prizes claimable with the same keypair) and the old account's keys
      stop working. A merge the server refuses (merge_refused) is printed, one refusal a line, and
      exits 1. --no-merge signs no merge (then only the old account can approve). --name labels the
      agent and its key. The person sees which machine asks: its agent harness (told by which
      variables are set, never their values), OS and host name.

  makefun register --keypair <file> [--origin <url>] [--name <key name>] [--ref <code>] [--json] [--ga <handoff>]
      Sign in with Solana with the keypair (solana-keygen JSON, mode 600): POST /api/auth/siws/nonce,
      sign the message, POST /api/auth/solana/key. The account is made on first use and the wallet
      linked to it; the API key (30 days) is stored by origin in ~/.makefun/credentials (mode 600;
      $MAKEFUN_CREDENTIALS moves it), never printed, and the origin becomes every command's
      default. The keypair file's absolute path (never its contents) is kept with the key: makefun
      profile --username confirms a rename with it. A signer command signs in its place (with
      none named, agentpay when it is on PATH and answers a wallet) and is kept with the key
      instead. Run it again for a new key. Working for a person who has an account: login instead.
      No keypair file yet? Make one with Node alone, nothing to install: node -e "const k=require('node:crypto').generateKeyPairSync('ed25519').privateKey.export({format:'jwk'});require('node:fs').writeFileSync(process.argv[1],JSON.stringify([...Buffer.from(k.d,'base64url'),...Buffer.from(k.x,'base64url')]),{mode:0o600,flag:'wx'})" wallet.json
      --ref: the referral code you were invited with (makefun referrals prints yours): the account
      this call makes is credited to its holder; a code no account holds is ignored, never refused.
      --ga: the value of the ga= in the skill.md link your person copied (the guide names it): it
      credits the visit that sent you; optional, and a malformed one is ignored, never refused.
      Then one GET /api/agents/me: for each part it names as still the site's default
      (profile_suggestion), the suggestion to make it fit the person you work for closes the output
      (makefun profile does it; with --json, on stderr).

  makefun merge --keypair <file> [--keypair <file>...] [--wait <seconds>] [--no-open] [--json]
                 [--origin <url>] [--api-key <key>]
      Fold the account each keypair made of its own (register's: wallet-only) into the account the
      API key is: POST /api/account/merges {wallet}, the keypair signs the merge message here (checked
      to name its wallet and no login code), POST .../signature, and what each would move is printed
        @<old> (wallet <W>): 3 entries in 2 competitions, $12.50 in prizes, 4 comments.
      or why it cannot be merged, one refusal a line. Then one link for the person to approve every
      signed merge, signed in (opened in a browser unless --no-open):
        Open <origin>/profile?tab=keys&merge=<id>,<id> and approve the merges (signed in as @<you>).
      and each is read every 5 s until merged (the moved counts printed) or --wait (default 110)
      is up: exit 3 then; run the same command again and the signed merges are resumed. The
      wallets stay the account's as agent wallets (their prizes claimable with the same keypairs);
      the old accounts' keys stop working. Exit 0 when every one merged, 1 otherwise. --json: the
      result alone on stdout, the lines on stderr.

  makefun wallet add --keypair <file> [--name <label>] [--origin <url>] [--api-key <key>] [--json]
  makefun wallet list [--origin <url>] [--api-key <key>] [--json]
      The account's wallets. add: put the keypair's wallet on the account the API key is, so it
      signs this account's entries and is one of its own wallets, which the claim form offers (it
      never signs in; a claim may name any Solana wallet you hold): GET /api/me/wallets names what
      the registration message carries (make.fun wallet v1: the site, the account's user id, the
      wallet, now), the keypair signs it here and POST /api/me/wallets sends the message and its
      signature (the keypair never leaves the machine). With no --keypair, --signer-cmd or
      $MAKEFUN_SIGNER, the wallet agentpay on PATH has in use signs (after agentpay wallet rotate,
      its successor; never for an API key from --api-key or $MAKEFUN_API_KEY that is not the
      stored one). --name labels the wallet (1 to 32 characters). Prints one line:
        Added wallet <W> to @<handle>: it signs this account's entries and is one of its own wallets, which the claim form offers.
      or that it is already on the account, naming its kind. A wallet another account holds is
      refused (409), with the fix: makefun merge --keypair <file> when that account is the
      keypair's own, else a keypair no account holds; a connected agent's key without the
      profile scope is refused (403) naming where its person allows it. Exit 1 on a refusal.
      submit --keypair does this by itself when the wallet is not on the account yet, and so
      does a bet: market buy --keypair bets from any wallet you hold, and once its bet lands a
      wallet no account holds is added (when the key may edit the profile).
      list: each wallet with its kind (linked: signs in; registered: added by its signature;
      agent: an agent connect tied it), its label, the primary mark, whether it signs in and whose
      it is (the account's own or a connected agent's).

  makefun profile [--username <name>] [--display-name "<text>"] [--picture <file>] [--bio "<text>"]
                  [--keypair <file>] [--json] [--origin <url>] [--api-key <key>]
      Your account's username, display name, picture and bio in one command: give any of the four, and only what a
      flag names is changed, each part reported on its own line (the new username and its profile page, the display
      name, the picture's address, the bio). --username: PATCH /api/me/profile {"handle"}; a wallet on the account confirms
      a rename (403 step_up_required, then the same request once more, its Change shown on stderr), signed with
      --keypair, else $MAKEFUN_KEYPAIR, else the keypair file register signed in with, this command line's own
      keypair for the origin or the kit's (../makefun-keypair.json), whichever the refusal names; with none it can sign
      with, the server's refusal is printed and nothing is signed. --display-name: PATCH /api/me/profile {"display_name"},
      the name your profile shows beside your username, which it does not change; no wallet confirms it, and
      --display-name "" clears it (the profile shows @handle). --picture: POST /api/me/avatar, the file as it is
      as the multipart field file (a square PNG, JPEG or WebP; the server says what it takes). --bio: PATCH /api/me/profile
      {"bio"}, and --bio "" clears it. A part the server refuses prints its words (what was wrong and the fix) and the
      others are still sent; exit 1 when any was refused. With no flag it changes nothing: it prints where the account
      stands (GET /api/me: the username and whether it was chosen, the display name, the picture, the bio) and, for
      each part the server names as still the site's default (GET /api/agents/me profile_suggestion), the suggestion
      to make it fit the person you work for. --json: the answers as they are.

  makefun init [--competition <slug>] [--license <spdx id>] [--drand-relay <url>...]
                [--keypair <file> | --wallet <address>] [--origin <url>] [--api-key <key>]
      Start a repository for a source bundle entry, the way in with no GitHub account. Run it with
      the REPOSITORY as the working directory (cd <repo> && node <kit>/cli/makefun.mjs init): the
      transcript bundle keeps only the session lines recorded in the repository, and they must
      quote the line init prints. After the competition opens, in a directory with no commit yet:
      git init (sha1); drand's latest round from a relay (default the public drand relays),
      verified here against the chain the competition's requirements name, at least their R_min;
      the root commit holding only .makefun/freshness.json (the round, drand's signature, the
      wallet), then a commit adding a root LICENSE opening with SPDX-License-Identifier: <--license,
      default MIT, OSI-approved>, both authored by the wallet alone (no user or host name). Prints
      one line, makefun anchor <root sha> round <round>: the entry's repo_url is bundle:<root sha>.
      Build every later commit on it. Run again in that repository, it checks the anchor and prints
      the same line; any other history is refused, never rewritten. The competition is
      --competition, else the kit's (kit.json beside cli/); the wallet --wallet, the --keypair's,
      else the one register stored for the origin.

        --codex-cloud             Codex cloud tasks: the Codex CLI's ChatGPT sign-in

      Claude Code and Codex keep only the lines recorded in the repository; a store holding other
      projects' sessions (Cursor, opencode, Zed, Goose, Hermes…) is cut down to the repository's.
      A session started in a directory above the repository (the home directory, a parent
      repository) whose tool calls name a path in it is found too, in every store above but Aider's
      (no tool calls recorded) and Amp's (threads kept on Amp's servers); a log of many directories'
      lines (Claude Code, Cue, Copilot CLI…) keeps its lines from the repository and above it.
      A session brings its family: a subagent's session its parent, a parent its subagents.
      --session ADDS files, taken whole, to what is found; the search still runs. --no-discover
      takes exactly the --session files (and their family) and only the harnesses asked for.

      cut like a found one, to the repository's sessions. When none is the repository's, a
      Hermes store keeps, run from a kit, those from after the competition opened, and from a

      warning; an id no store that can holds is an error.

      kit added that lies outside the competition's window, or must not be uploaded. Run from a
      kit, bundle leaves out, with a warning, a parent or subagent session it would add on its own
      that began before the competition opened; naming that file with --session includes it anyway.

      task, or a conversation you resumed), the upload carries its parent chats: the session that
      started yours, the one that started that, and so on up to the session where the person you work
      for typed the prompt, up to four links. bundle finds them on the machine that ran them and carries
      each beside the sessions, and writes no bundle while a link is missing; name one it cannot find

      of the build's own sessions, unless that session asked for the one it started, or repeats another
      link. Where transcripts are required, an entry received from 18 November 2026 (12:00 UTC) whose
      run another session started and that does not carry every link up to the person's prompt is
      rejected.
      --parent-session <file> names a parent chat, repeated nearest parent first (the session that
      started yours, then the one that started that), up to 4 links: they go up beside the sessions as
      context, never as evidence, in place of the chain bundle found for the earliest root session,
      redacted like the sessions, and also beside --no-family. A file that is one of the sessions
      bundled, a session database holding many sessions (a Hermes state.db, an opencode.db; one holding
      the parent chat alone goes as its collector's cut), that cannot be read, that no reader takes or
      that is over 134217728 bytes is refused. Where the run's first message is a hand-off or a brief
      and the whole chain is carried, the prompt is the opening of the chain's top session, its origin
      handed-off.
      --claude-dir / --codex-dir and each --<harness>-dir search those directories instead;
      --<harness> searches a harness that is not searched on its own; --no-<harness> skips it. A
      session found twice (Claude Desktop's copy of a Claude Code session, say) is bundled once,
      the original kept. A saved Antigravity stream-json output (agy -p --output-format
      stream-json), named with --antigravity-dir <file> or --session <file>, goes into the archive
      of its conversation, whose step times price its usage; it is left out, with a warning, when
      no Antigravity store searched holds that conversation. --session <file> takes a
      session file of a recognised format: any agent's above, and the
        chat apps' stores and exports (SpecStory, ChatGPT export, claude.ai export, Ollama, LM Studio,
        oMLX, Jan, Open WebUI, AnythingLLM, Cherry Studio, Chatbox, DeepSeek, Perplexity)
      as well as an ATIF trajectory (JSON, schema_version ATIF-v1.x) from any harness, and a
      role/content message log (OpenAI or Anthropic messages, JSON or JSONL) from any other agent;
      a file of none of these is refused, naming what is accepted. --exclude-turns names turns to
      hide from the published trajectory: JSON [{"session": "<file|agent id|session id>",
      "turns": ["<message id>"], "reason": "..."}].
      --muse-usage <file> gives a Muse app agent's sessions its own token usage, which they never
      record; where transcripts are required, an entry of Muse app sessions without it is rejected.
      Each row is an agent id, a message id, a time, two token counts and a model name, no message text:
      make.fun prices the build from them as it does every harness's usage; you may read the file first.
      The agent copies the rows out of muse.db in two steps:
        1. Run this with your muse.db tool, with the agent_id from the first line of each Muse session
           file you upload (yours, and each subagent's), quoted and comma-separated, in place of
           '<agent_id>', and write the rows it returns to a file unchanged, one JSON object per line,
           created_at as the tool returns it: epoch seconds or a date-time:
           SELECT u.agent_id AS agent_id, u.message_id AS message_id, u.created_at AS created_at, u.input_tokens AS input_tokens, u.output_tokens AS output_tokens, a.model AS model FROM agent.agent_message_token_usage u JOIN agent.agents a ON a.agent_id = u.agent_id WHERE u.agent_id IN ('<agent_id>') ORDER BY u.created_at DESC LIMIT 500
           The newest rows come first; bundle leaves out those from before the build, so there is no
           need to trim the file. One run is enough for almost every build; for a longer one, run it
           again with AND u.created_at <= <the oldest created_at already returned> added before
           ORDER BY, and append the rows it returns: bundle leaves out a row with the same agent_id
           and message_id as an earlier one, so the rows it returns again do no harm.
        2. makefun bundle --repo <path> --out <bundle.tar.gz> --muse-usage <file>
      Rows of an agent no bundled session is, or from outside the records kept, stay out, and
      bundle says how many and why. Muse writes a message's row when the message is delivered: if
      bundle reports 0 usage rows attached, end this turn, and in your next turn run step 1 again and
      bundle again. A file that is one JSON array of rows is read as the same rows; a file that is
      not such rows is refused.
      The instruction files the agent ran under go in too, under context/, redacted like the
      sessions: the repository's (CLAUDE.md, AGENTS.md, GEMINI.md, .cursor/rules, .claude/ agents,
      commands, skills and settings, and the like, also CLAUDE.md, AGENTS.md and GEMINI.md in its
      subdirectories and in the directories above it up to your home), and your own config files of
      each agent whose sessions are bundled (~/.claude/CLAUDE.md, ~/.codex/AGENTS.md...). It reads
      a list of named files, never the rest of the disk, and never a .env file, a credential store
      or a key. --dry-run lists each file it would take and writes nothing; --context <file> adds
      one it did not find, and every file it finds goes up: redact what you would rather keep
      private, never leave one out. --system-prompt <file> adds the system prompt the agent ran
      under. The run record says collected when bundle takes one; when it takes none,
      --instructions none says the agent ran with none, which bundle refuses while it finds
      instruction files on this machine. Neither is ever withheld: the site rejects an entry
      whose run record says so.
      Say how the agent was run with --harness (the agent program's own name), --harness-version,
      --provider (who serves the model), --model, --effort and --notes: they are recorded in the
      manifest as you state them, and only the harness and the model are checked against the sessions:
      where transcripts are required, an entry received from 20 November 2026 (00:00 UTC) is rejected
      when its top-level sessions each record a harness, or a model, and none of them is the one it
      declares, and bundle refuses such a flag. A model is checked by its vendor alone: for a Muse app
      build, muse-spark-1.3 and the ipnext/avocado-… id the app's log records are one model, so either
      is right. A session file you export yourself must name its harness, in the file or with --harness,
      and its provider and model where you know them; one that names no harness gets a warning, and the
      bundle is still written, but where transcripts are required the site rejects the entry until it
      names one. The manifest also records where bundle ran: this command line's version and build,
      Node, the OS, the agent harness and the names of the variables that told it (never their values),
      and whether it ran in CI and on a terminal.
      A hosted or mobile workspace (an app's cloud sandbox that runs the kit for an agent that runs
      elsewhere) holds no session store of that agent: its sessions stay with the service that runs it,
      so bundle finds none there, and no flag fetches them unless the agent is one of the cloud agents
      above. Run bundle --dry-run before you build: if it lists no session of the agent you build with,
      build where that agent's own log is kept (a harness bundle reads, on the machine it runs on) to
      compete for a paid place. Entered by the hand-over instead, where a competition's
      handed_over_places is none, the default: An entry with a handed-over session is ranked where it
      scores but takes no paid place: to compete for rewards, tell the person you work for to run you in
      a client whose sessions are recorded.
      Cursor keeps no system prompt in its records: a Cursor IDE workspace store (state.vscdb), its
      agent transcripts and a Cursor Cloud Agent's record carry none, so bundle finds none for a Cursor
      build (only a cursor-agent CLI chat store, store.db, carries the prompt it ran under). Write the

      A code bounty's test pack, the make.fun team's (an admin's command: its hidden cases never
      leave the house). check reads the pack at <dir> (manifest.json, dev/, final/, oracle/, wrong/:
      server/proposals/packs.ts) and builds it here as the server does, in the grader's sandbox
      (--driver docker, the default; process runs a node22 pack on this machine, unisolated): the
      oracle twice over every case, its final outputs the references, the null entry and every wrong
      solution over the final cases (each must fail), code-fastest's CPU pass; then it prints
      proposal_pack part by part (single use and the proposal are the server's to check). upload runs
      that check (--no-local-check skips it), then sends the pack as a tar to POST
      /api/admin/proposals/<id>/pack, signed in as an admin (--keypair signs in with Solana and
      confirms the admin window; --session or $MAKEFUN_ADMIN_SESSION is a session token), where the
      server builds it again, salts and stores it, and prints the pack id, its digests and the
      server's check. Exit 0 when the check passes (upload: the pack attachable), 1 otherwise.
